# Power Trace Explorer data-submission guide

This guide describes the public-import format for LLM training and inference
power traces. It separates information supplied by a contributor from package
records generated by the import builder.

## What a contributor supplies

For every run, provide:

1. An original GPU telemetry CSV in `raw/<run_id>.csv`.
2. A factual metadata JSON record in `metadata/<run_id>.json`.
3. For inference runs, an optional request timeline in
   `requests/<run_id>.csv` or event-level request data from which the builder
   can derive that timeline.

Do not estimate or fill in missing measurements. Use JSON `null` or an empty
CSV cell when a field was not recorded. Preserve the source telemetry's
sampling cadence and values.

## Package layout

The completed, validated package has this form:

```text
LLM-Power-Trace-Import-v1-<contributor>-<YYYYMMDD>/
├── raw/<run_id>.csv
├── metadata/<run_id>.json
├── requests/<run_id>.csv        # optional inference timeline
├── runs/<run_id>.json           # normalized browser payload
├── catalog.json
├── publication-audit.json
├── import-manifest.json
├── submission.json
└── README.md
```

`raw/` and `metadata/` are contributor inputs. `requests/` is optional.
`runs/` and every top-level JSON or Markdown file are generated or validated
by the import builder; contributors should not hand-author them.

| File | Created by | Purpose |
| --- | --- | --- |
| `catalog.json` | Builder | Index of every normalized run in the package. |
| `publication-audit.json` | Builder/reviewer | Records validation and release status. |
| `import-manifest.json` | Builder | Lists every packaged file with byte counts and SHA-256 checksums. |
| `submission.json` | Builder | Identifies the contributor, package version, and import context. |
| `README.md` | Builder | Human-readable package summary and instructions. |
| `runs/<run_id>.json` | Builder | Browser-ready run metadata, normalized samples, and optional inference timeline. |

## GPU telemetry CSV

Use this canonical column set whenever values are available:

```text
run_id,timestamp,time_relative_s,gpu_id,power_w,sm_clock_mhz,gpu_util_pct,
memory_util_pct,memory_used_mb,memory_total_mb,temperature_c,stage
```

The minimum useful fields are `run_id`, a time representation (`timestamp`
and/or `time_relative_s`), `gpu_id`, and `power_w`. The builder normalizes
compatible source schemas, but the original values must remain unchanged.

## Per-run metadata

Each metadata record describes one real experiment or serving run. Use values
from the experiment configuration, job record, or serving log—never inferred
values. A minimal inference example is:

```json
{
  "run_id": "example-vllm-h100-tp4-burst-001",
  "workload_type": "inference",
  "model": "Llama-3.1-8B-Instruct",
  "gpu_type": "H100 SXM",
  "gpu_count": 4,
  "serving_engine": "vLLM",
  "workload_pattern": "BurstGPT serving window",
  "tensor_parallel_size": 4,
  "kv_cache_quantization": "FP8",
  "model_weight_quantization": "AWQ INT4",
  "gpu_frequency_mhz": 1410,
  "concurrency": 64,
  "in_flight_requests": 64,
  "arrival_rate_rps": null,
  "prompt_tokens": null,
  "output_tokens": null,
  "requests_completed": null,
  "total_tokens_processed": null
}
```

Training records keep the established fields such as `model`, `precision`,
`compute_dtype`, `sequence_length`, `microbatch_size`, `grad_accum_steps`,
`dataset_name`, and checkpoint information.

## Inference request timeline

The website displays request arrivals and request size beneath the GPU-power
trace when the optional timeline exists. Its columns are:

```text
time_relative_s,window_s,requests_arrived,active_requests,
mean_prompt_tokens,mean_output_tokens,mean_request_tokens
```

- `time_relative_s`: start of the reported time window, aligned to GPU power.
- `window_s`: duration of the time bin in seconds.
- `requests_arrived`: number of requests that arrived in the bin.
- `active_requests`: concurrent/in-flight requests, when recorded.
- `mean_prompt_tokens`, `mean_output_tokens`: mean token counts for requests
  in the bin.
- `mean_request_tokens`: mean total request size. The builder can derive it
  from prompt plus output tokens.

If your source logs are event-level instead, provide `request_id`, arrival
time (or `time_relative_s`), `prompt_tokens`, and `output_tokens`; completion
time, latency, and status are optional. The builder can aggregate these events
into the published timeline.

For a local event CSV, the included helper writes the standardized timeline:

```bash
npm run normalize:inference-requests -- \
  --input request-events.csv \
  --output requests/<run_id>.csv \
  --window-s 5
```

## Submission and review

1. Prepare the contributor inputs locally.
2. Run the import builder and inspect its validation output.
3. Upload the completed unpacked package to the designated staging folder.
4. Reviewers verify metadata, package structure, and checksum manifest.
5. Only consented and approved records move to the public catalog.
